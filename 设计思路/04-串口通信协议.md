# 04 串口通信协议

默认：`/dev/mascdc`，115200，8 数据位、无校验、1 停止位（8N1）。

> `/dev/mascdc` 是 udev 创建的软链接，不是系统自带的设备名。
> 如果它不存在、或实际设备名变成了 `ttyACM0` / `ttyUSB1`，请看第 5 节《串口设备与联调排查》。

所有多字节字段均为**小端**（little-endian），结构体使用 `__attribute__((packed))` 紧凑排列。

## 1. 发送包：视觉 → 电控（`DartSendPacket`）

| 偏移 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| 0 | header | uint8 | 帧头 `0xBB` |
| 1 | found | uint8 | `1` = 选中的目标可见或已锁定 |
| 2 | target | uint8 | `0` = 无，`1` = 前哨站（两个最大目标中偏左），`2` = 基地（偏右） |
| 3 | state | uint8 | `0` = idle，`1` = acquire（角度有效），`2` = hold（电控保持不动） |
| 4 | target_yaw_deg | float32 | 云台需要转过的角度，**单位：度**；hold 时恒 `0` |
| 8 | tail | uint8 | 帧尾 `0x5B` |

总长 **9 字节**。

### state 的含义

| state | 含义 | 电控应该怎么做 |
| --- | --- | --- |
| 0 | 没有目标选择，视觉不输出瞄准 | 保持不动 |
| 1 | 正在粗对准 | 用 `target_yaw_deg` 驱动云台，让角度趋近 0 |
| 2 | 已对准并锁定 | **保持当前角度不动**，不要继续跟随目标 |

`state = 2` 是这次改动的核心：底座只在开闸后**粗对准一次**，
锁定之后基地目标再怎么随机移动，底座都不再动——后续由制导镖负责。

- `target_yaw_deg > 0`：目标在图像中心右侧，飞镖架应向右转；
- `target_yaw_deg < 0`：目标在左侧，应向左转；
- 角度由 `yaw_sign * atan2(center_x - cx, fx)` 算出后从弧度转成度；
  方向反了改 `track.yaw_sign = -1.0`；
- 电控直接把这个角度当误差做 PID 即可；角度依赖 `fx`，`fx` 标定不准会有比例误差。

## 2. 接收：电控 → 视觉（单字节命令）

没有包头、包尾、保留字节，**每收到一个字节就是一条命令**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| command | uint8 | `0` = 待机；`1` = 前哨站；`2` = 基地；`3` = 重新粗对准 |

视觉只接受 `0~3`，其它字节（噪声、乱码）直接丢弃。

### 发送方式建议

- **周期发送当前目标状态**（例如 50~200ms 一次）：`0/1/2`。
  视觉收到重复值会忽略，不会反复触发状态机；
  切换目标最迟一个周期就能生效，也能自动补齐丢字节、视觉晚启动、串口重连的情况。
- **`3` 是动作，不是状态**：只在需要重新粗对准时发一次；
  不要周期发送 `3`，否则会一直清掉 HOLD，永远锁不上。
- 如果电控一直不发任何数据，视觉使用 `config/dart_vision.yaml` 里的
  `track.default_target`（默认 `0` = 待机）。

### 单字节协议的风险

没有帧同步，线上出现 `0~3` 的随机字节会被当成命令，导致目标短暂切错；
因为电控周期发送，下一个周期就会纠正。适合"串口只传这一个命令"的专用链路。
如果以后这条串口还要传别的数据，建议恢复包头包尾或加校验。

## 3. 发送频率

`threads/serial_thread/serial_thread.cpp` 固定 **250 Hz**（每 4ms 发一次，
内容为最近一次 `sendDart()` 写入的最新值）。若需修改频率，改 `send_interval`。

## 4. 和旧协议的区别

| 旧 | 新 |
| --- | --- |
| 12 字节，`found / error_x / target_yaw(rad) / reserved` | 9 字节，`found / target / state / target_yaw_deg` |
| 同时发 `error_x` 和 `target_yaw` | 只发一个角度（度），电控直接当误差用 |
| `command` 只有 0/1（停止/启动跟随） | 单字节 `command`：0/1/2/3（待机/前哨站/基地/重新对准），周期发送状态，3 只发一次 |
| 目标持续跟随 | 粗对准后进入 HOLD，底座固定不动 |

## 5. 串口设备与联调排查（踩坑记录）

> 这一节是实际联调时踩出来的，设备名这一块**换机器、换线、拔插之后都可能不一样**。
> 后续维护者遇到"双向收不到数据"时，按这里的顺序查，别一上来怀疑协议或代码。

### 5.1 `/dev/mascdc` 不是天然存在的

`config/serial_config.yaml` 里默认写的是：

```yaml
port: "/dev/mascdc"
```

这个路径**不会自动出现**，它是 `scripts/setup_serial_device.sh` 生成的 udev 软链接。
以下情况它都会不存在：

- 设备没插 / USB 线只供电不走数据；
- 从没跑过 udev 脚本；
- 拔插或重启后 udev 还没来得及触发；
- 换了另一块板子（VID/PID/序列号不匹配 udev 规则）。

路径不存在时，`serial::Serial` 构造会抛异常，`UserSerial` 会进入
`reconnect()` 的 5 秒重试循环，表现为日志每 5 秒刷一次：

```
Attempting to reconnect to serial port...
Exception while reconnecting to /dev/mascdc: IO Exception (2): No such file or directory
```

注意此时**程序其它功能都正常**（相机、检测、界面都在跑），很容易误以为
"发了但对方没收到"，实际是一个字节都没发。

### 5.2 设备名会变：`ttyACM0` vs `ttyUSB0`

| 设备类型 | Linux 下的名字 | 说明 |
| --- | --- | --- |
| USB 转串口芯片（CH340 / CP2102 / FT232 等） | `/dev/ttyUSB0`、`/dev/ttyUSB1`… | 所谓"USB 虚拟 COM 口"，线上仍是真实 UART 波形 |
| 单片机原生 USB CDC（STM32 等） | `/dev/ttyACM0`、`/dev/ttyACM1`… | USB 直连，不涉及外部 TX/RX 电平 |
| 板载 UART | `/dev/ttyS0` 等 | 需要确认 pinmux 与权限 |
| socat / pty 纯软件虚拟串口对 | `/dev/pts/N` | 没有物理层，两端必须各开一端 |

编号由内核枚举顺序决定：**拔插、换 USB 口、同时插多个设备都会变**。
本项目联调时实际设备是 `/dev/ttyACM0`，但**不能假设下次还是它**。

查当前实际设备：

```bash
ls -l /dev/ttyUSB* /dev/ttyACM* 2>/dev/null
ls -l /dev/serial/by-id/ 2>/dev/null     # 最稳定的路径，按芯片序列号命名
dmesg -T | tail -30                      # 插拔前后的枚举日志
lsusb                                    # 芯片是否被识别
```

### 5.3 看懂串口库的报错码

日志里的 `IO Exception (N)` 里的 N 是 Linux 的 errno：

| errno | 名称 | 含义 | 先查什么 |
| --- | --- | --- | --- |
| 2 | ENOENT | 路径不存在 | 设备名写错、`/dev/mascdc` 没建、USB 没插 |
| 13 | EACCES | 权限不足 | 用户不在 `dialout` 组、设备权限不是 0666 |
| 16 | EBUSY | 设备被占用 | `sudo lsof /dev/ttyACM0`，关掉 minicom/socat/旧进程 |
| 5 | EIO | I/O 错误 | USB 掉线、线材接触不良、板子重启 |

### 5.4 三种修复方式

**① 直接改配置（联调最快）**

```yaml
serial:
  enable: true
  debug: true          # 联调期间建议打开，能看到收到的原始字节
  port: "/dev/ttyACM0" # 换成 ls 里实际看到的设备名
```

**② 临时软链接（不改配置）**

```bash
sudo ln -sf /dev/ttyACM0 /dev/mascdc
ls -l /dev/mascdc      # 确认 mascdc -> ttyACM0
```

缺点：拔插 / 重启后失效，udev 会清掉 `/dev` 下的手工链接。

**③ udev 固定名称（长期）**

```bash
./scripts/setup_serial_device.sh
# 用普通用户运行，不要 sudo；脚本内部会自己提权
# 输入设备路径，例如 /dev/ttyACM0
# 输入固定名称，例如 mascdc
```

然后拔插一次设备，确认 `ls -l /dev/mascdc` 出现。脚本会同时把用户加入
`dialout` 组（**需要重新登录或 `newgrp dialout` 才生效**）。

### 5.5 更稳的做法：用 by-id 路径

USB 设备序列号不变的话，`/dev/serial/by-id/...` 永远指向同一块板子，
不受枚举顺序影响：

```yaml
port: "/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0"
```

多个串口设备（相机云台、电控、裁判系统…）同时在线时，优先用 by-id。

### 5.6 权限

```bash
ls -l /dev/ttyACM0          # 期望 crw-rw---- root dialout 或 crw-rw-rw-
groups | grep dialout       # 当前用户是否在组里
sudo chmod 666 /dev/ttyACM0 # 临时放行，重启失效
```

### 5.7 改完配置必须重启程序

`UserSerial` 是单例，配置只在**第一次构造时**读一次
（`hardware/serial/user_serial.cpp` 构造函数），运行中修改 yaml 不会生效，
`reconnect()` 也不会重读。改完 `serial_config.yaml` 一定要重启进程。

启动日志里要能看到这两句：

```
Serial config loaded successfully from: ...
Reconnected to /dev/ttyACM0
```

并且不再刷 `Attempting to reconnect`。

### 5.8 双向不通时的排查顺序

1. **配置路径存在吗？** `ls -l /dev/mascdc`（或配置里写的实际路径）
2. **串口打开成功了吗？** 日志有没有 `Reconnected to ...`，还刷不刷 reconnect
3. **自己真的发了吗？**
   ```bash
   sudo timeout 3 strace -f -p $(pgrep -x dart_vision) -e trace=write -s 32 -xx 2>&1 | head -20
   ```
   期待每 4ms 一条 `write(..., "\xbb...\x5b", 9) = 9`。
4. **对方的数据进来了吗？** `debug: true` 下日志应有 `Received N bytes (HEX): ...`
5. **绕过程序直接看串口**（先停掉程序，避免抢数据）：
   ```bash
   stty -F /dev/ttyACM0 115200 raw -echo
   timeout 5 cat /dev/ttyACM0 | xxd -g1
   ```
   什么也没有 → 问题在对方发送 / 线缆 / 波特率，不在解析代码。
6. **本机回环自测**（仅 USB 转串口模块，能引出 TX/RX 引脚时）：
   把模块的 TX 和 RX 短接，`enable/debug` 打开后运行，日志应刷出自己发的 9 字节帧
   `BB ... 5B`。能收到 → 本机收发链路正常，问题在接线或对方；
   收不到 → 本机配置 / 驱动 / 权限问题。
7. **`ttyACM0`（USB CDC）额外注意**：必须是**数据线**；`dmesg` 里要有
   `cdc_acm ... ttyACM0: USB ACM device`；电控固件里 CDC 已初始化且确实在调用发送。
   CDC 不涉及 TX/RX 交叉与电平转换。
